# Test Data — Renegotiation Process Homologation

This document defines the 10 test customers used to homologate the conversational renegotiation flow (WhatsApp → `whatsapp-bff` → `conversation-orchestrator` → `agent-runtime-renegotiation` → `tool-service-renegotiation` → `renegotiation-service` → `core-bancario-mock`).

Each customer is identified by a reserved tax ID (the same digit repeated 11 times), resolved deterministically in `core-bancario-mock/Program.cs` (`ScenarioFixtures.ByCpf`) — see `openspec/changes/validate-renegotiation-flow-scenarios/design.md` for the rationale. Any tax ID outside this list continues to use the generic data historically generated by the mock.

The phone number is arbitrary (the webhook simulator in `postman/microservices.postman_collection.json` accepts any value in `messages[0].from`; it is not a number registered with Meta). Use the sequence below for convenience and log/transcript traceability.

The tax ID is provided by the customer in the text message (`text.body`), as it would be in a real conversation — it is not carried in the webhook payload's `from` field.

## Scenario details

### 0 — `00000000000` — Customer not found
- **Mock data**: `GET /clients/00000000000` → `404`.
- **Suggested script**: "My tax ID is 00000000000, I want to renegotiate my debt."
- **Expected**: the agent says it could not locate the customer and does not proceed to contracts/debts.

### 1 — `11111111111` — Standard happy path
- **Mock data**: 1 contract (`emprestimo_pessoal`, balance R$ 2,500.00); 1 debt (R$ 950.00, 45 days overdue); eligible.
- **Suggested script**: "My tax ID is 11111111111, I want to renegotiate my debt." → accept the simulation proposal suggested by the agent → confirm the agreement.
- **Expected**: positive eligibility, simulation presented, successful confirmation, document link available.

### 2 — `22222222222` — Multiple contracts and debts
- **Mock data**: 2 contracts — `emprestimo_pessoal` (balance R$ 6,000.00, debts of R$ 1,500.00/40d and R$ 800.00/70d) and `cartao_credito` (balance R$ 3,200.00, debts of R$ 900.00/20d and R$ 500.00/50d).
- **Suggested script**: "My tax ID is 22222222222, I want to renegotiate my debt."
- **Expected**: the agent identifies more than one contract/debt and asks which one the customer wants to renegotiate, or lists the options, before simulation.

### 3 — `33333333333` — Ineligible due to critical delinquency
- **Mock data**: 1 contract (balance R$ 12,000.00); 1 debt (R$ 4,000.00, 300 days overdue); `Eligible: false`, `Reason: cliente_inadimplente_critico`.
- **Suggested script**: "My tax ID is 33333333333, I want to renegotiate my debt."
- **Expected**: the agent tells the customer they are not currently eligible for renegotiation and does not offer a simulation.

### 4 — `44444444444` — Low-value debt / short delay
- **Mock data**: 1 `cartao_credito` contract (balance R$ 300.00); 1 debt (R$ 85.00, 5 days overdue); eligible.
- **Suggested script**: "My tax ID is 44444444444, I want to renegotiate my debt."
- **Expected**: flow proceeds normally despite the low value; simulation is offered and can be completed.

### 5 — `55555555555` — High debt / severe delay
- **Mock data**: 1 contract (balance R$ 25,000.00); 1 debt (R$ 18,500.00, 210 days overdue); eligible.
- **Suggested script**: "My tax ID is 55555555555, I want to renegotiate my debt."
- **Expected**: flow proceeds normally; observe whether the agent adapts its wording to the high value/delay without incorrectly refusing the journey.

### 6 — `66666666666` — No open debt
- **Mock data**: 1 contract (balance R$ 5,000.00); empty debt list.
- **Suggested script**: "My tax ID is 66666666666, I want to renegotiate my debt."
- **Expected**: the agent says there are no open debts to renegotiate and does not offer a simulation.

### 7 — `77777777777` — Simulation expires before confirmation
- **Mock data**: 1 contract; 1 debt (R$ 1,300.00, 35 days). `POST /simulations` generates a `simulationId` containing the `-expired` marker, so `POST /confirmations` is always denied with `simulation_expired`.
- **Suggested script**: "My tax ID is 77777777777, I want to renegotiate my debt." → accept the simulation → confirm the agreement.
- **Expected**: the simulation is presented normally; on confirmation, the agent receives the expiration denial and should explain it and offer a new simulation without leaving the conversation stuck.

### 8 — `88888888888` — Document pending after confirmation
- **Mock data**: 1 `cartao_credito` contract (balance R$ 3,500.00); 1 debt (R$ 2,100.00, 50 days). `POST /confirmations` is accepted, but the generated `agreementId` includes the `-pendente` marker, so `GET /agreements/{id}/document` returns `document_not_ready`.
- **Suggested script**: "My tax ID is 88888888888, I want to renegotiate my debt." → accept the simulation → confirm the agreement.
- **Expected**: agreement confirms successfully; when requesting the document, the agent says it is still being generated and tells the customer to wait rather than reporting an error.

### 9 — `99999999999` — Requested installments outside allowed range
- **Mock data**: 1 contract; 1 debt (R$ 1,000.00, 25 days); eligible. This scenario does not depend on fixed tax-ID data — any simulation with `installments > 48` or `<= 0` is rejected by the mock (`installments_out_of_range`). The reserved tax ID exists only to provide a separate reproducible test row.
- **Suggested script**: "My tax ID is 99999999999, I want to renegotiate my debt in 60 installments."
- **Expected**: the agent explains that 60 installments are not possible and negotiates a number within the allowed limit (up to 48).

## How to use

1. Start the complete local stack according to `docs/runbook.md` § 4, with `MOCK_AGENT_ENABLED=false` and a valid `OPENAI_API_KEY` (see the `renegotiation-flow-homologation` capability).
2. For each summary-table row, send the suggested script through a signed `POST /webhooks/whatsapp` request using the Postman helper from the previous E2E validation and the table's `from` value.
3. Record the response transcript and observed result in `docs/validation/<date>-renegotiation-scenario-homologation.md`, comparing it with the expected business outcome in this document.
