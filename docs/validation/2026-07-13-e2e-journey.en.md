# E2E Journey Validation — 2026-07-13

Real execution of the complete journey (webhook → `whatsapp-bff` → Kafka → `conversation-orchestrator` → `agent-runtime-renegotiation` → `tool-service-renegotiation` → `renegotiation-service` → `core-bancario-mock` → response) against all seven application services and infrastructure running simultaneously, comparing observed behavior with what `docs/runbook.md` and `docs/architecture/sequence-diagrams.md` claimed. Corresponds to OpenSpec change `validate-e2e-microservices-journey`.

## Environment and method

- **Mode:** the full stack was already running through `docker compose up -d` when validation started — reused rather than restarted to preserve the state of an environment already in use.
- **Agent Runtime:** `MOCK_AGENT_ENABLED=false` in the container with a real `OPENAI_API_KEY` configured for `gpt-4o-mini`. The happy path therefore used real OpenAI reasoning rather than deterministic keyword fallback. `MOCK_AGENT_ENABLED=true` was not exercised in this run; Agent Runtime unavailability fallback (`agent_runtime_unavailable`) was validated separately by stopping the container.
- **Ports:** Docker Compose ports were used, not the local-development ports previously documented in `docs/runbook.md` §3.

## Documentation findings corrected in this change

1. **Docker Compose ports were undocumented.** `conversation-orchestrator` and `renegotiation-service` are exposed at host ports `5268`/`5266`, unlike local-development ports `8000`/`9400`. Corrected in the runbook, Orchestrator service page, and sequence documentation.
2. **Degradation time was described as "200ms" while actual failure could take ~30s.** `MaxRetryAttempts=2, Delay=200ms` did not describe the total budget; `AddStandardResilienceHandler` defaults (`AttemptTimeout=10s`, `TotalRequestTimeout=30s`) dominated hanging failures. Observed Agent Runtime DNS failure took ~5–8s and Handoff attempts ~30s. Documentation was corrected.
3. **Audit call was documented as active but commented out in code.** `IngestMessageUseCase.cs` injects `IAuditServiceClient`, but `RecordJourneyEventAsync(...)` was commented. Related documentation was corrected.
4. **Local WhatsApp Cloud API delivery failure lacked an explicit warning.** Notes were added to the runbook and `whatsapp-bff` documentation.

## Code findings not fixed in this change

### 1. Duplicate-processing risk for the same inbound message — medium/high severity

`whatsapp-bff` used `AttemptTimeout=10s` for Orchestrator `POST /messages`. The Orchestrator endpoint was synchronous end-to-end and could exceed that timeout with real OpenAI latency plus delivery attempts. The client then retried, while the Orchestrator had no `MessageId` deduplication. The same message (`wamid.validation-run-1`) was therefore processed **twice**, producing separate Jaeger traces and separate OpenAI calls, potentially doubling LLM cost and side effects.

**Suggested follow-up:** deduplicate by `MessageId`, increase the client timeout, and/or make `/messages` genuinely asynchronous by returning `202` before Agent Runtime processing.

### 2. Dead audit call in code — low severity

The Orchestrator's call to `auditClient.RecordJourneyEventAsync(...)` was commented. `audit-service-mock` worked when called directly but received nothing during normal operation.

**Suggested follow-up:** either reactivate the call using the existing resilience pattern or remove the dead dependency.
